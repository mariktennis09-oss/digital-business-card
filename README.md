# Цифровая визитка — GraphQL API

Бэкенд-визитка: профиль специалиста, навыки, опыт работы и проекты, доступные
через GraphQL и Apollo Sandbox.

**Стек:** TypeScript · Node.js · NestJS · Prisma · PostgreSQL · GraphQL (code-first) · Docker

- Sandbox (развёрнутая версия): _ссылка добавляется после деплоя_
- Исходный код: https://github.com/mariktennis09-oss/business-card-website-
- Контракт API: [`schema.gql`](./schema.gql) — сгенерирован из кода и закоммичен

---

## Запуск с нуля одной командой

```bash
docker compose up --build
```

Поднимается Postgres, дожидается healthcheck, затем контейнер приложения
применяет миграции, заполняет базу и стартует. После старта:

- Apollo Sandbox — http://localhost:3000/graphql
- Healthcheck — http://localhost:3000/health

Никаких ручных шагов между `up` и работающим API нет.

## Запуск без Docker

```bash
cp .env.example .env          # значения по умолчанию совпадают с docker-compose
npm ci
npm run prisma:generate
npm run db:setup              # миграции + сид
npm run start:dev
```

Нужен доступный PostgreSQL. Проще всего поднять только базу:
`docker compose up -d db`.

## Проверки

```bash
npm run lint         # ESLint + Prettier
npm run typecheck    # tsc --noEmit, strict
npm run schema:check # закоммиченный schema.gql не разошёлся с кодом
npm test             # unit-тесты, база не нужна
npm run test:e2e     # e2e через настоящий стек, нужна база
```

`npm run test:e2e` сам применяет миграции и сид перед запуском (см.
`test/global-setup.ts`); базу можно задать отдельно через `DATABASE_URL_TEST`.

## Примеры запросов

Запрос из технического задания:

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Всё, что есть в схеме, включая фильтр навыков и вычисляемые поля периода:

```graphql
query {
  profile {
    name
    description
    links {
      label
      url
    }
    skills(category: BACKEND) {
      name
      category
    }
    experience {
      company
      position
      period
      isCurrent
      durationMonths
      startDate
      endDate
      achievements {
        text
      }
    }
    projects {
      name
      repoUrl
      liveUrl
      description
    }
  }
}
```

## Архитектура

```
src/
  config/       валидация окружения (zod), единственное место с process.env
  prisma/       PrismaService + глобальный PrismaModule
  common/       GraphQL-контекст, декоратор лоадеров, фильтр ошибок Prisma
  profile/      корень схемы: Query.profile и вложенные поля
  skill/        навыки
  experience/   опыт работы, достижения, DataLoader, арифметика периода
  project/      проекты
  health/       /health с проверкой базы
prisma/         schema.prisma, миграции, сид и данные сида
scripts/        генерация schema.gql из метаданных резолверов
api/            точка входа для Vercel
web/            сайт-визитка на Next.js — потребитель этого API
```

`web/` к тестовому заданию отношения не имеет: ТЗ требует бэкенд, и всё, что
оценивается, лежит в корне. Фронтенд — отдельное приложение со своими
зависимостями, своим линтом и своим деплоем; бэкенд о нём не знает и в
Docker-образ он не попадает.

Внутри каждого feature-модуля три слоя:

| Слой           | Отвечает за                                             |
| -------------- | ------------------------------------------------------- |
| **Resolver**   | контракт GraphQL: типы, аргументы, поля                 |
| **Service**    | доменные правила и публичный контракт модуля            |
| **Repository** | доступ к данным; единственное место с вызовами Prisma   |

Правила, которые держат разделение честным:

- **Prisma не поднимается выше репозитория.** Ни сервис, ни резолвер не знают
  о `PrismaClient`.
- **Чужой репозиторий недоступен.** `ProfileResolver` ходит в `SkillService`,
  `ExperienceService`, `ProjectService` — не в их репозитории. Поэтому сервис
  существует даже там, где он тонкий: это граница модуля, а не украшение.
- **Абстракция появляется там, где что-то преобразуется.** Отдельного маппера
  Prisma → GraphQL нет: типы `@ObjectType()` написаны руками и развязаны с
  таблицами, а вычисляемые поля живут в чистом модуле `experience.period.ts`,
  который резолвер вызывает напрямую. Обёртка-сервис поверх чистых функций не
  добавила бы ничего.

### Вложенные данные и N+1

Вложенные коллекции разрешаются через `@ResolveField`, то есть лениво: запрос
`profile { name }` не делает ни одного лишнего похода в базу.

DataLoader применяется ровно там, где N+1 математически возможен — на уровне
вложенности с несколькими родителями. Такое место в схеме одно:
`Experience.achievements`. Остальные коллекции висят на singleton-профиле, у них
родитель ровно один, и лоадер там был бы обрядом. Экземпляр лоадера создаёт
context-фабрика GraphQL-модуля на каждый запрос: DataLoader кэширует, и его
время жизни обязано совпадать с временем жизни запроса.

### Модель данных

`Profile` — singleton с фиксированным `slug`; на нём висят `Skill`,
`Experience`, `Project` и `ProfileLink`, а на записи опыта — `Achievement`.

- `Achievement` и `ProfileLink` — отдельные таблицы, а не массивы строк и не
  фиксированные колонки `githubUrl`/`linkedinUrl`: у них своя идентичность и
  свой порядок, а список площадок расширяется без миграции.
- Период работы хранится как `startDate` + `endDate?`; `isCurrent`,
  `durationMonths` и `period` вычисляются, а не хранятся.
- `SkillCategory` — enum на уровне БД и GraphQL: Sandbox подсказывает
  допустимые значения по интроспекции, а опечатка в фильтре не вернёт молча
  пустой список.

## Инициализация и заполнение базы

- Миграции версионированные (`prisma/migrations/`), применяются через
  `prisma migrate deploy` — не `db push`.
- Сид (`prisma/seed.ts`) работает на голом `PrismaClient`, без контекста Nest:
  подготовка базы не должна зависеть от того, поднимается ли приложение.
- Данные лежат в типизированной константе `prisma/seed-data.ts`.
- Точек запуска три, скрипт один: `npm run db:setup` локально, entrypoint
  контейнера, `vercel-build` на деплое.

Стратегия — **полный resync в транзакции**: дочерние записи удаляются и
создаются заново, `Profile` обновляется upsert-ом по `slug` (чтобы у singleton
не менялся `id`). Upsert всего подряд оставил бы в базе строки, удалённые из
`seed-data.ts`, — и API отдавал бы не то, что написано в репозитории.

## Что стоит знать при чтении

- **Интроспекция и Sandbox включены в проде намеренно.** По умолчанию
  NestJS/Apollo отключает их при `NODE_ENV=production`, и тогда требование
  «предоставить Apollo Sandbox» не выполнялось бы на развёрнутой ссылке. API
  read-only, мутаций и секретов нет.
- **Миграции и сид выполняются при каждом старте контейнера**, без отдельного
  init-job. При одной реплике (как в `docker-compose`) это безопасно:
  `migrate deploy` защищён advisory-lock Postgres, а сид идемпотентен. При
  масштабировании до нескольких реплик их следовало бы вынести в отдельный job,
  выполняемый один раз до старта приложения; здесь это осознанно не сделано как
  избыточное.
- **У проекта два поля ссылок, а не одно.** ТЗ называет поле «ссылка на
  проект/репозиторий» — это два независимых факта, «где код» и «где посмотреть
  живьём». Инвариант «хотя бы одна ссылка» выражен типом `ProjectSeed`: запись
  без обеих не пройдёт компиляцию.
- **`period: String` — presentational-хелпер**, а не замена структурным полям.
  Форматированная строка не сортируется и не считается, поэтому `startDate`,
  `endDate`, `isCurrent` и `durationMonths` остаются в схеме.
- **Njord Group и «Дом у моря» встречаются дважды** — в опыте (роль и
  достижения) и в проектах (артефакт и ссылка). Для фриланс-истории это разные
  грани одного заказа, а не дубль.
- **Порядок вывода не выражен полем в API.** Он закодирован позицией в
  `seed-data.ts` и колонкой `order` в базе; клиент получает уже упорядоченные
  списки и не может их рассинхронизировать.
- **Стека самой визитки (NestJS, Prisma, GraphQL, Docker) нет в списке
  навыков.** Он показан этим репозиторием, а не строчкой в данных.

## Лог инженерных решений

Только развилки, где отвергнута очевидная альтернатива.

| Решение                                                     | Вместо чего                          | Почему                                                                                                       |
| ----------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| Singleton `Profile` по фиксированному `slug`                 | параметризация по id/slug            | одна визитка одного человека; top-level `skills` подразумевал бы мир из многих профилей, которого нет          |
| Полный resync сида (`delete` + `create` в транзакции)        | upsert всех записей                  | код — единственный источник правды; upsert оставляет удалённые из `seed-data.ts` строки                        |
| Сид вне рантайма на Vercel (только `vercel-build`)           | сид в `OnModuleInit`                 | холодные старты, гонки параллельных инвокаций, read-only FS                                                    |
| Миграции и сид при каждом старте контейнера                  | отдельный init-job                   | реплика одна, `migrate deploy` advisory-lock-safe; отдельный job — избыточен для объёма                        |
| DataLoader только на `Experience.achievements`               | DataLoader везде / `include` везде    | N+1 возможен только там, где на уровне вложенности несколько родителей                                         |
| Prisma-enum `SkillCategory`                                  | свободная строка                     | самодокументируемый контракт в Sandbox; опечатка в фильтре не молчит. Цена — миграция при реклассификации      |
| `@ObjectType()` руками, отдельного маппера нет               | кодогенерация / маппер на агрегат     | контракт GraphQL эволюционирует независимо от схемы БД; маппер 1:1 — тот же боилерплейт, от которого уходим    |
| Структурные поля периода + тонкий `period: String`           | только форматированная строка         | сервер не фиксирует формат отображения, но ТЗ называет поле «период» — отсюда хелпер поверх дат                |
| `repoUrl?` + `liveUrl?` с инвариантом на уровне типа         | единое поле `url`                    | код и деплой — два независимых факта о проекте, не один факт с типом-меткой                                    |
| Порядок опыта — правило в сервисе, а не `orderBy`            | сортировка в SQL                     | «текущие первыми, затем по дате начала» в SQL выражается только через NULLS FIRST — правило пришлось бы вычитывать из строки orderBy |
| Конкретные классы репозиториев                               | интерфейс + DI-токен                 | второй реализации нет и не планируется; тесты подменяют конкретный класс через `useValue` так же легко          |
| Read-only API, без мутаций и auth                            | полноценный CRUD                     | это визитка; силы уходят в качество слоёв и корректный запуск с нуля                                            |
| Опыт как фриланс-заказы, а не штатные должности              | синтетические работодатели            | штатных мест не было; `company` — реальный заказчик                                                             |
| Prisma CLI в прод-зависимостях                               | только dev-зависимость               | entrypoint применяет миграции при старте контейнера, значит CLI нужен в рантайм-образе                          |

## Деплой на Vercel

Пошагово провести по обоим дашбордам умеет `scripts/deploy-wizard.sh`: он
открывает нужные страницы, объясняет, что нажимать, принимает обе строки
подключения, дописывает `pgbouncer=true`, если его забыли, и в конце сам
дёргает `/health` и запрос из ТЗ по развёрнутому адресу.

```bash
bash scripts/deploy-wizard.sh
```

Значения он пишет в `.env.deploy.local` — отдельно от `.env`, где лежит адрес
локальной базы для разработки.

На Vercel исполняется serverless-функция (`api/index.ts`), а не Docker-образ;
Dockerfile и compose остаются для локального запуска и как документированный
рантайм. Функция поднимает тот же `AppModule` и ту же настройку, что и
`main.ts`, — конфигурация между двумя средами не форкается.

Переменные окружения:

| Переменная     | Где нужна          | Значение                                          |
| -------------- | ------------------ | ------------------------------------------------- |
| `DATABASE_URL` | runtime + build    | pooled endpoint Neon, с `?pgbouncer=true`         |
| `DIRECT_URL`   | **build-time**     | direct endpoint Neon, для `migrate deploy` и сида |

`DIRECT_URL` обязан быть доступен на этапе сборки, а не только в рантайме:
миграции и сид выполняются в `vercel-build`.

Фронтенд разворачивается **вторым проектом Vercel из того же репозитория**:
Root Directory — `web`, единственная переменная — `API_URL` с адресом
развёрнутого GraphQL.

## Фронтенд (`web/`)

Сайт-визитка на Next.js 15 (App Router), TypeScript, Tailwind v4, three.js
и GSAP. Разделы адресуются хешем (`#/`, `#/work`, `#/about`, `#/contact`),
фон — GPGPU-поле частиц на curl noise.

```bash
cd web
cp .env.example .env.local   # API_URL, по умолчанию локальный бэкенд
npm ci
npm run dev
```

Отдельный стенд для сцены: `/lab/particles` — только canvas, счётчик кадров
и переключатель числа частиц.

### Решения

- **Данные приходят из GraphQL на сборке**, а не дублируются в коде: правка
  в `prisma/seed-data.ts` доезжает до сайта сама. Страница остаётся
  статической, открывается мгновенно и не ложится, если бэкенд спит.
- **Обычный `fetch` вместо GraphQL-клиента.** Кеш данных Next цепляется
  именно к нему: `next.revalidate` работает только так. Клиент поверх забрал
  бы эту интеграцию, а взамен не дал бы ничего — запрос ровно один.
- **Симуляция целиком на GPU.** Позиции лежат во float-текстуре и обновляются
  фрагментным шейдером через ping-pong двух render target. Поле скоростей —
  ротор симплекс-шума: он бездивергентен, поэтому частицы не сбиваются в комки.
- **Один кадровый цикл.** Симуляция, реакция на курсор и рендер идут в одном
  `useFrame`; своего `requestAnimationFrame` нигде нет.
- **Глитч написан руками**, без библиотеки композера: проход ровно один.
  При нулевой интенсивности прохода нет вовсе — сцена рисуется прямо на экран.
- **Переход — один таймлайн**, а не одновременный фейд: уход контента, всплеск
  глитча и реакция поля внахлёст, приход нового. Частицы не перезапускаются.
- **Клиентского состояния минимум.** Курсор, энергия перехода и интенсивность
  глитча живут в `ref`: их читает кадровый цикл, и перерисовывать ради них
  дерево React нечего.
- **Никаких внешних шрифтов в рантайме.** `next/font` скачивает их на сборке
  и раздаёт со своего домена.

### Доступность и запас прочности

- `prefers-reduced-motion` — поле замирает, глитч и дешифровка выключаются,
  переход сводится к фейду 150 мс. Содержимое доступно полностью.
- Без WebGL 2 сцена не поднимается, фон подменяется статичной растяжкой.
  Весь текст живёт в DOM: canvas — фон, а не носитель информации.
- Качество снижается по измеренному кадру, а не только по догадке о железе.
- Поле останавливается в скрытой вкладке и вне вьюпорта.
- Меню — обычные ссылки: работает клавиатура, «назад» и прямой адрес.

## Тесты

- **Unit** — только содержательная логика: арифметика периода, правило порядка
  опыта, батчинг DataLoader, валидация окружения. Прокси-методы не тестируются.
- **E2E** — дословный запрос из ТЗ (чтобы соответствие условию проверялось
  само), фильтр навыков с аргументом и без, вложенные достижения с вычисляемыми
  полями, инвариант ссылок проекта, форма ошибки и `/health`.
